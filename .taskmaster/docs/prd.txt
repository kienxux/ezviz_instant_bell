# UPDATE 2026-11-13 (reordered)

The user asked to prioritise, as local as possible: (1) getting the ring into Home
Assistant locally, and (2) two-way talk. The task order in tasks.json now leads with
those two. Key research result of 2026-11-13:

- Two-way talk on this hardware is CLOUD-MEDIATED, not a plain LAN channel. The EZVIZ
  talk client connects to a talk server with a CAS verify + ECDH + P2P handshake (the
  same path as the cloud live relay). The LAN ports 9010/9020 carry only video+listen
  (INIT/INVITE/PLAY). The public EZVIZ Open SDK does talk only through its cloud player
  and needs a developer appKey; pyezvizapi has no send path. So local talk is very
  unlikely; the realistic routes are the official appKey SDK or a reverse-engineered
  cloud CAS talk path (large). Next step: one FRITZ!Box capture of the app talk button.
- Local ring: the CPD5 was captured and rings are cloud-only; the HP7 was never captured
  at a ring. Worth one passive capture (UDP 50160/50162 + a FRITZ!Box trace) at a real
  ring before concluding HP7 = cloud-only too.
- Do NOT run native-library disassembly inside an assistant session (a safety filter
  stops it). Use the public SDK/docs and passive captures with the user present.

The sections below are the earlier, fuller plan; the stream work (release 1.2.1, confirm
numbers, offline corruption) is unchanged, now tasks 3-5.

# ezviz_instant_bell — work plan after the first real LAN sessions (2026-11-13)

Owner of the plan: the lead session. Any agent may take one task; take the smallest open task whose
dependencies are done, work on a branch, and report back with the branch name and the test result.

## Where we stand

- 1.2.0 is released (local start without the cloud, 1 s probe, 8 s dead detection). The user says it is
  "stable and quick now". The Advanced Camera Card issue was the card's own bug (fixed by updating it).
- We can now open real LAN sessions with the HP7 from this container. The harness is
  `/tmp/lanlive/lanlive.py`; its secrets (LAN key, stream key) live in `/tmp/lanlive/secrets.env`,
  are never printed, and never go through a chat session. The harness only works while Home Assistant
  does not hold the session: the door station allows ONE local client (INVITE Result 1052683 means
  "already taken").
- Three real-device findings sit on branch `local-live-fixes` (worktree `/tmp/ezviz-lanfix`,
  uncommitted, 362 tests green, verified on the HP7):
  1. the clear-NAL-header-size detection must see >= 16 KB before deciding (we use 24 KB); on ~1 KB it
     is wrong about half the time, which made every reopened session a coin toss;
  2. the decoder must sync on the pack header when the stream is encrypted (every SPS is ciphertext,
     so waiting for a clear SPS took 8–110 s); with the fix it syncs in 0.12 s;
  3. INVITE Result 1052683 gets a readable hint ("another local viewer holds the session").
- Still unknown: why a running session turned to garbage about 3 min after the station lost its
  internet link (SPS bytes changed, "Overread VUI by 8 bits", then intra errors on every frame).
- Answered by the harness: the 180 s "Interval" in INVITE is not a keepalive we have to serve; the
  session passed the mark twice without being closed.

## Rules for every task

- Never fast-scan the door station (its LAN daemon died once from a parallel scan). One connection at
  a time, pauses between tries, small ranges, and the user's go-ahead for anything that sends commands
  other than INIT/INVITE/PLAY.
- Keys are credentials: they stay in `/tmp/lanlive/secrets.env` or in Home Assistant's storage. Scripts
  may read the file; they print lengths, never values. Nothing with a key goes into git or a chat.
- A harness run needs Home Assistant stopped (or its local session closed). Ask the user first.
- Tests: `python -m pytest -q tests` locally, and the GitHub run (HA 2026.2.3 and the "oldest" job on
  2025.9.0) is the real check. Guard registry calls with hasattr (see CLAUDE.md / memory).
- 1.x promise: entity IDs, events, actions and options stay; breaking changes wait for 2.0.
- Never copy code from tarasifua/ezviz_rtsp (Apache-2.0); ideas only.
- CHANGELOG "Unreleased" entry with every user-visible change, written for owners, not developers.

### T3 — Offline corruption: find the cause and fix it
Needs the user to block the door station's internet on the FRITZ!Box. Two harness runs:
(a) start online, block after 1 min, keep running 6 min: does the stream change at ~3 min after the
block (SPS fingerprint per window)? (b) start fresh while blocked (>3 min after the block): does it

decoder when the SPS fingerprint changes (or when ffmpeg reports "Overread VUI"); fresh-broken → the
device encrypts differently offline, dump analysed inside HA, and the README says what to expect.
Depends on T1 (sync-on-pack must be in).
